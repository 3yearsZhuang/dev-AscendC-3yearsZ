# 任务契约与真实计分

新题、换赛区、评分或模板变化时读取。契约是便于复查的项目记录，不要求每次 Tile 微调重新调研所有字段。可复制 [JSON 示例](../assets/contest-profile.example.json) 后填真实证据；它是人工记录结构，提交脚本不会自动执行其中全部配置。

## 先确定工程与语义

读取题面、下载工程中的参考实现/比较器、Host 入口与在线模板，记录它们的路径、版本/SHA 和核实时间。

| 类别 | 会影响实现的内容 |
|---|---|
| 目标 | group/contest/problem ID 与完整 URL，用户要正确性基线、最高官方分、诊断还是最终交付 |
| 环境 | 芯片、CANN/Bisheng、可用核数、是否真机可用；没有证据的值保留未知 |
| 输入输出 | dtype 编码、shape/属性域、广播、布局、别名、精确 GM 分配、尾部是否实际 padding |
| 数值 | 参考 dtype 与逐步舍入、比较器/容差、NaN/Inf/正负零要求 |
| 入口 | `run_kernel` 签名、真实宏/类型、传入 stream、只读文件；kernel 启动次数、workspace/ACL 限制按题目规定 |
| 开发来源 | 用户本次允许/指定的文档；题面与日志作为任务事实，不自动继承旧任务的唯一教程 |

`npu_kernel_dev` 的 dtype 数值由该模板定义，不能直接套 `ge::DataType`。框架已定义的类型、入口和主函数不要重复注册。传统算子才走其 Host/Kernel/tiling 结构。

## 评分决定晋升

- 读取题目的 `ranking_submission_mode`、比赛的排名规则和可见范围。`best`、`last` 与全通过门槛是不同维度；不得从 ACM/OI 名称推断。
- 保存官网选定的 submission ID 与评分，不用本地耗时求和替代。总榜分、题目分、回执 `score`、`theory_score` 可能含义不同，保留原字段和来源。
- 非 Pass 是否有分需官方规则或真实榜单证据；确认允许后可为排名目标选择部分通过候选，仍保留完整正确性回退版并披露失败覆盖。
- best 模式也要检查平台实际选中了谁；last 模式的新提交可能替换旧成绩，实验顺序按用户目标安排。
- 可见点总数与完整点数分别保存。仅 5 点返回且都通过，结论为“可见 5/5，另 10 点未公开”，不是全 15 点已验证。顶层终态也不补足隐藏点证据。

## 配额与协作

配额、重置时区、冷却和截止时间要从当次平台信息核实。`theory_quota_limit` 不能自动解释为代码提交配额。旧错误中的 50 次/日或 180 秒不写成永恒默认值。以明确拒绝中的 `reason`、`retry_after_seconds` 为本次依据。

同账号跨题或跨聊天可能争用额度。一个协调者负责 POST，其他 agent 只做实现和离线检查。每次发送前检查已知在途请求、最新账号记录与冷却；平台不可确认是否受理时先处理未知请求。脚本对某个 attempt 的防重放不能阻止浏览器或另一主机提交。

## 判读示例

以下是假设场景，用于说明如何记录证据；不代表任何赛区的实时配置：

- 题面确认共 15 点，接口只公开 5 点且全部通过：记录“可见 5/5，另 10 点未知”，并保存原始返回；不能宣布全量通过。
- 官方榜单明确显示某条 Wrong Answer/Runtime Error 获得正分：可以据此确认该条记录获得部分分数，仍不能推导隐藏计分公式或推广到其他比赛。
- 主源码与旧 verified-result 的 SHA 不一致：旧记录不能用于当前源码晋升，应重新绑定并检查；哈希变化本身不证明算法错误。
